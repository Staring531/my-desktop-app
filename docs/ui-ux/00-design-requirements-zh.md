# UI/UX 设计需求

- 状态：设计基线，不构成产品范围变更。
- 依据：已批准 PRD（DEC-011）、Technical Design 和 Implementation Plan。
- 目的：明确桌面应用如何呈现已批准的 Version 1 行为。

## 原则
1. PRD 是用户可见行为的唯一权威，不得增加功能、角色、流程或业务规则。
2. Technical Design 决定架构、进程边界、数据所有权、持久化和安全约束。
3. 仅设计一台电脑上的一个团队、成员/邀请生命周期、单次日程事件、可见性和忙闲视图。
4. 未经用户明确修改已批准文档，Website、Admin、API 不是 Version 1 UI。
5. 不增加登录、邮箱验证、多团队、同步、提醒、重复/全天事件或其他已排除行为。
6. 设计规格不等于实现授权；不得编写应用代码、安装依赖或修改 Implementation Plan。
7. 区分已确认需求、提案、假设和待确认问题。
8. 每个页面和交互都追溯到 PRD 需求和已批准技术契约。

## 必须交付
信息架构、用户流程图、页面清单/规格、先低保真后高保真线框、交互和 UI 状态规格、轻量设计系统、无障碍和桌面窗口要求、PRD/Technical Design/Implementation Plan 追溯、独立评审和用户明确批准。

## UI 状态
按需覆盖初始、加载、有数据、空状态、校验错误、操作错误、禁用、成功、无权限和数据不可用。不得为未批准行为凭空增加状态。

## 阶段门槛
Readiness Analysis 只做分析。结构设计审阅通过后才能做高保真设计。设计包完整后进行独立评审。用户明确批准前保持 READY FOR USER REVIEW。UI/UX 获批不授权编码。

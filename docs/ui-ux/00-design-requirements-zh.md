# UI/UX 设计需求

- 状态：设计基线，不构成产品范围变更。
- 依据：已批准 PRD（DEC-011）、Technical Design 和已确认的 Implementation Plan。
- 目的：明确桌面应用如何呈现已批准的 Version 1 行为。

## 原则
1. PRD 是用户可见行为的唯一权威，不得增加功能、角色、流程或业务规则。
2. Technical Design 决定架构、进程边界、数据所有权、持久化和安全约束。
3. 仅设计已批准的单团队、单电脑 Version 1 行为，以及文档规定的成员、邀请、事件、可见性和忙闲流程。
4. 未经用户明确修改已批准文档，Website、Admin、API 不是 Version 1 UI。
5. 不增加登录、邮箱验证、多团队、同步、提醒、重复/全天事件、主题偏好或其他已排除行为。
6. 设计规格不等于实现授权；不得编写应用代码、安装依赖或修改 Implementation Plan。
7. 区分已确认需求、提案、假设和待确认问题。
8. 每个页面、组件和交互都追溯到 PRD 需求和已批准技术契约。
9. 遵循 System-First 顺序：结构 → 已批准视觉方向 → 已批准 Token/核心组件 → 页面设计 → 验证/评审。
10. Linear 仅作为视觉参考，不复制品牌资产或增加产品专属功能。

## 必须交付
就绪分析报告；信息架构和用户流程图；页面清单；获批视觉方向；Primitive/Semantic/Component Token 基线；可复用组件契约；低保真线框；高保真页面规格；交互/UI 状态规格；无障碍和桌面窗口要求；需求追溯；设计系统验证；独立评审；用户明确批准。

## UI 状态
按需覆盖初始、加载、有数据、空状态、校验错误、操作错误、禁用、成功、无权限和不可用。不得为未批准行为凭空增加状态。

## 阶段门槛
Readiness Analysis 只做分析。结构设计审阅后才能开展视觉系统工作。用户先批准 Visual Direction，再提出最终 Token；用户批准 Token/核心组件后，才批量开展高保真页面设计。完整设计包经独立评审。用户明确批准前保持 READY FOR USER REVIEW。UI/UX 获批不授权编码。

# UI/UX 工程标准

- 版本：1.0.0-draft
- 状态：试点标准；先在本仓库验证，再决定是否推广。
- 适用范围：本仓库内所有包含用户界面的应用。除明确标注 Electron/React 的条款外，均为技术栈无关要求。
- 规范用语：MUST = 强制要求，作为发布门禁；SHOULD = 原则上应遵守，例外须记录审批；MAY = 可选实践。

## 1. 治理与权威来源

1. 已批准的产品需求定义产品行为；已批准的设计包定义预期视觉与交互行为。实现不得暗中改变两者。
2. 每个项目必须明确产品、技术和设计的事实来源、负责人、审批状态和版本。
3. 涉及层级、字体、间距、颜色、交互、可访问性或组件行为的设计变更，必须先记录并评审。
4. 偏差必须记录原因、影响页面/组件、风险、批准人、复审日期及验收证据。
5. 本标准统一工程质量，不统一视觉主题。不同项目可以有不同品牌、密度、布局和组件语言。

## 2. 设计系统要求

1. 每个 UI 项目必须定义 Primitive、Semantic、Component 三层 Token，或说明某层不适用的原因。
2. Primitive 表达原始尺度和值；Semantic 表达用途；Component 表达组件级设计决策。
3. 页面应优先消费 Semantic 或 Component Token。仅当没有合适语义别名时，才允许直接使用基础 Primitive；重复使用时应补充语义别名。
4. 组件必须定义适用状态：default、hover、focus-visible、active、disabled、pending、error、selected；不适用的状态应注明。
5. 布局必须定义支持的最小窗口/视口尺寸，并防止意外溢出、控件裁切和不稳定换行。
6. 可访问性必须覆盖语义结构、键盘操作、可见焦点、可访问名称和适用的 WCAG 对比度要求。

## 3. Token 数据源与运行时要求

1. 项目必须指定唯一 Token 数据源（JSON、类型化数据或设计 Token 平台）。生成的运行时文件不得成为第二个可编辑数据源。
2. Token 命名必须稳定、分层、表达用途并有文档。别名必须可解析，不得存在循环或缺失引用。
3. 运行时 Token 必须由唯一数据源生成，或通过确定性的校验器证明手工维护文件保持同步。
4. CI 必须对非法 Token、未解析别名、重复名称、缺失的运行时 Token 和生成文件漂移报错。
5. 颜色、字体、字号、间距、尺寸、边框、圆角、阴影和动效等设计决策必须消费运行时 Token。display、overflow、box-sizing、width:100%、margin:0 等布局机制和 reset 不必 Token 化。
6. Token 例外必须局部化、说明理由并记录。不得随意引入一次性视觉值。

## 4. 组件与页面实现

1. 当重复使用或共享行为确有价值时，必须抽取可复用组件。
2. 组件必须消费设计 Token，并提供可访问名称、标签、焦点行为和状态反馈。
3. 页面必须建立清晰层级：页面目的、主要任务/数据、辅助信息和次要操作。
4. 密集数据必须采用稳定列、受约束的 Grid/Flex 或明确的响应式变体；不得默认依赖无约束 flex 自动换行组织结构化记录。
5. 适用时必须设计并测试空、加载、等待、成功、校验、权限和失败状态。
6. 必须在最小支持视口和代表性大视口测试布局行为。

## 5. 需求到运行时追溯

1. 每个重要页面、覆盖层和关键交互必须有稳定标识符。
2. 追溯注册表必须将页面/交互 ID 关联到需求、业务规则、流程、设计规范、组件、源文件、后端操作和测试。
3. 后端映射必须反映真实架构（例如 REST/API、IPC/preload、service、domain、persistence）；不得把非 HTTP 架构强行抽象成 REST。
4. 追溯元数据必须集中维护在单一注册表或生成产物中，不得散落硬编码在页面组件里。
5. 必须校验 Schema、重复 ID、缺失引用和失效的源文件/测试路径。
6. QA 人员必须能够检查当前页面，并追踪其需求、设计、renderer、后端操作和测试证据。生产环境是否暴露调试元数据必须受到明确控制。

## 6. 验证与验收

1. Build、typecheck、lint 和单元测试是必要工程检查，但不能证明视觉验收通过。
2. 每个页面必须在真实目标运行时和支持的视口尺寸下验证。涉及桌面/移动平台行为时，浏览器预览不能替代目标运行时验证。
3. 视觉验证必须包含命名截图、视口/运行时信息，以及与批准设计参考或明确验收标准的比较。
4. 关键流程必须有自动化交互或集成测试；后端/domain 行为必须在实际实现层验证。
5. 人工验收必须检查功能、视觉层级、内容、响应式、键盘/焦点、可访问性和追溯。
6. 验收状态必须区分 PASS、FAIL、BLOCKED、NOT RUN。缺少证据属于 NOT RUN，绝不能标记为 PASS。
7. 未解决的 MUST 级失败或未经批准的偏差必须阻止发布。

## 7. 标准采用与试点验证

1. 项目采用标准时，必须记录标准版本、适用范围、偏差及实施/验证计划。
2. 试点必须记录发现的问题、误报、漏报、自动化覆盖率、评审耗时和标准修订项。
3. 在宣布标准稳定并推广之前，必须依据试点发现修订标准。
4. 本仓库的 Electron/React 桌面应用是第一个试点。在宣称跨技术栈验证成功前，必须再选择一个有实质差异的 UI 技术栈进行验证。

## 8. 本仓库试点配置

- 唯一 Token 数据源：\`docs/ui-ux/tokens/design-tokens.json\`。
- 运行时目标：Electron renderer CSS custom properties。
- 追溯数据源：\`docs/traceability/ui-traceability.json\`。
- 视觉和页面权威文档：\`docs/ui-ux/05-visual-design.md\`、\`docs/ui-ux/12-page-specifications.md\`。
- 产品与业务权威来源：已批准 PRD、业务规则和验收标准文档。
- QA Inspector 仅用于开发/验收，不是产品功能。

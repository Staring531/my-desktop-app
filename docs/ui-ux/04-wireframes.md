# Wireframes

## Purpose
Define layout, hierarchy, and task sequence before visual styling. Wireframes are proposals and must not settle product questions silently.

## Coverage
Cover all approved screens or document justified combinations; supported desktop window sizes; primary/secondary/destructive/disabled actions; keyboard focus; validation and recovery; applicable empty/loading/success/no-access/error states.

## Per-screen template
1. Screen ID/name and actor/preconditions.
2. Primary task and supporting information.
3. Layout regions and hierarchy.
4. Controls and action semantics.
5. Validation and feedback placement.
6. State variants.
7. Keyboard/accessibility behavior.
8. PRD AC and Technical Design references.
9. Open questions and alternatives.

## Fidelity progression
Text sketch → low-fidelity wireframe → user review of IA/task sequence → high-fidelity visual specification after structural baseline acceptance.

Do not use a static generated image as the sole source of truth for editable layout, component semantics, or interaction behavior. Keep source artifacts reviewable and maintainable.

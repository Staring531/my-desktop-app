# UI/UX 设计工作流

> 版本：3.0.0  
> 状态：正式工作流定义  
> 范围：为一个已批准的产品 PRD 制定 UI/UX 规格，不包含应用实现。适用于本仓库的每个产品和项目，也适用于所有由本工作流启动的新项目（第 8 节）。  
> 设计方式：System-First，以简报为先，以证据为准。每个产品在 `09-visual-references.md` 中记录自己的视觉简报和参考来源。

## 1. 权威依据、启动条件与启动协议

仅当 PRD、Technical Design 已获批准且 Implementation Plan 已存在时，才能在用户明确要求后启动。所有参与 Agent 必须先阅读 `docs/process/DEVELOPMENT_WORKFLOW.md`、`AGENTS.md`、本文件、已批准 PRD/Decision Log、Technical Design/评审、Implementation Plan，以及相关仓库和 package 文档。

权威顺序：已批准 PRD（行为和范围）→ 已批准 Technical Design（架构和技术契约）→ 已确认 Implementation Plan（任务顺序）→ 用户批准的 UI/UX 决策（仅呈现和交互）。

不得修改更高权威文档。发现产品歧义时询问用户；发现技术冲突时记录并通过 Technical Design 工作流请求修改。设计提案、Gate 完成、Reviewer PASS 或文档 PR 合并都不等于用户批准。

## 2. 不可违反的约束

- 保持正在设计的产品已批准 PRD 范围，不增加该 PRD 排除的行为。
- 只设计该产品已批准 PRD 和技术设计点名的界面。另一个产品已批准的界面不在范围内。
- 不编写应用代码、不安装依赖、不改变架构/PRD、不静默修改 Implementation Plan。
- 未经单独授权，不提交、推送、合并或发布。
- 设计提案或 Reviewer finding 不等于用户批准。
- Skill 是可复用流程，不是隔离 subagent。无法原生委派时必须披露，不得将自检称为独立评审。
- 除非已批准 PRD 包含，否则不得擅自假设深色模式、主题切换、新设置或新产品界面。响应式行为遵循已批准需求所指明的平台和支持的视口或窗口尺寸。
- 参考只提供可观察的特征和已记录的来源。不采用该来源的名称、标志、文字标志、品牌色，以及本产品没有的对象。
- 每条设计约束都必须归类为范围（Scope）或品味（Taste）（第 4A 节）。只有范围约束才会约束后续的视觉重设计。

## 3. Agent 角色与职责

### UI/UX Designer — 主设计 Agent / 调度者
主会话是唯一面向用户的设计者。负责检查现有 UI 代码/资源/组件/样式/测试；执行就绪分析；与用户一起写视觉简报；维护正式设计文档；保证设计系统一致性和 PRD AC → 流程 → 页面 → 组件/交互追溯；产出 Stage 6 要求的渲染证据；委派评审；处理 findings；向用户提出产品决策问题。不得编写应用代码或修改已批准 PRD/Technical Design。

### UI/UX Design Reviewer — 独立只读评审
仅在 Design Review Gate 调用。检查正式文档、视觉简报和渲染截图证据，只返回 findings。不得编辑文件、访谈用户、作产品决策或编写代码。平台支持时使用工具级只读限制；仅靠提示词不构成沙箱。

不新增设计 Agent。UI/UX 阶段不激活 Implementation Planner。

## 4. System-First 设计原则

设计系统是有约束力的设计契约，不是可选风格指南。

1. 先确认仓库约束和已批准产品结构，再作视觉决策。
2. 提出方向之前先确认视觉简报（Stage 2）。简报写明产品应该给人什么感觉，以及绝不能给人什么感觉。
3. 最终 Token 值必须在用户批准某一个方向的可打开页面集后提出。这些值从该页面集提取，并按 Stage 3 扩展。
4. 批量高保真页面设计前，必须由用户批准 Design Token 基线和核心组件模式。
5. 页面必须使用语义 Token 和已批准组件规范，避免任意页面数值和一次性组件。
6. 所有视觉/交互选择都要追溯到已批准 PRD 行为和 Technical Design 契约。
7. 参考提供可观察的特征和已记录的来源。已批准的可打开页面集是该方向的视觉权威。参考图片不能替代可编辑规格、Token 数据、组件契约或用户批准。
8. 若技术栈已有设计系统或组件库，应先调研并在适当时复用；设计阶段不得安装或替换依赖。
9. 视觉质量以渲染结果为准。Token 检查、追溯检查和文字描述都不能证明视觉质量。

### 4A. 范围约束与品味约束

- **范围约束：**来自已批准的 PRD 或 Technical Design（被排除的行为、界面、数据字段、平台限制、无障碍义务）。它约束每个设计阶段，只能通过所属工作流修改。
- **品味约束：**视觉偏好，例如栏宽、是否有导航外壳、卡片或层级的使用、信息密度、颜色、动效、参考族。它连同批准日期记录在视觉简报中。用户可以通过批准替换页面集来取代它，取代时不需要修改 PRD 或 Technical Design。
- 设计记录和交接文档必须分别列出这两类。品味约束应写成已记录的偏好，不得写成读起来像范围的禁令。只有当 PRD 排除了导航外壳将承载的目的地时，导航外壳才是范围问题。

## 5. 阶段与用户审批 Gate

### Stage 0 — 就绪分析
检查 UI 框架/renderer、导航、可复用组件、样式、字体/图标/资源、平台窗口或视口约束、无障碍模式、UI 测试和实施任务依赖。输出 Readiness Report、候选 IA 和页面清单、AC 到流程/页面/交互的初步映射、可复用资源、约束、风险和待确认问题。本阶段只分析：不决定视觉方向、不画线框、不写代码、不安装依赖、不修改计划。完成后等待用户审阅。

### Stage 1 — 信息架构、用户流程和页面清单
定义导航、角色入口、用户旅程、进入/退出条件、适用 PRD 流程和候选页面。每个流程/页面映射需求和 AC 编号。产品行为不确定时记录问题，不得通过编造 UI 自行解决。视觉系统工作开始前，先取得用户对结构基线的认可。

### Stage 2 — 视觉简报与 Visual Direction（用户审批 Gate 1）

**视觉简报。**提出方向之前，在 `09-visual-references.md` 中记录：受众和使用场景；产品气质的三到五个形容词；反目标（产品绝不能给人的感觉，例如普通文档或通用表单页）；信息密度；外壳和导航倾向；平台和支持的视口；品牌资产和硬性约束；以及所有品味约束。简报须经用户确认。用户没有偏好时，由设计者提出简报，再由用户确认。没有确认的简报，不得开始提出方向。

**方向。**至少提出两个方向。方向之间要在布局倾向、信息密度和表现力上不同，不能只是参考网站不同。至少有一个方向在层级、表面和色彩运用上是当代、有表现力的。不存在默认参考族。每个方向记录参考来源和归属、采用的可观察特征，以及排除的品牌元素和外来对象。覆盖信息密度、层级、布局倾向、字体方向、色彩策略、图标、表面和交互气质。

**页面集。**批准前，每个方向都包含一个可打开的页面集，页面使用已批准产品实际返回的字段：
1. 主工作屏幕；
2. 入口或表单屏幕（登录、创建或编辑）；
3. 展示失败、破坏性操作、空状态以及等待或成功状态的重状态屏幕或面板；
4. 产品有多个目的地时，包含导航外壳。

用户批准的是某一个方向的页面集。只有一张原则表，或只有单个页面，不能完成本关。没有记录来源、没有确认的简报或没有可打开页面集的方向是不完整的。

不得把临时颜色当成已批准 Token。等待用户明确批准某一个方向的页面集后再继续。早期工作流版本下已批准的视觉方向，在用户按本版本批准替换方案之前，仍是该产品的权威。

### Stage 3 — Design Tokens 与核心组件系统（用户审批 Gate 2）
Gate 1 通过后，从已批准的页面集提取 Primitive、Semantic、Component 三层 Token。覆盖颜色、字体、间距、尺寸/布局、圆角、边框、层级、图标、动效/减少动态效果和图层。

已批准 PRD 或 UI/UX 工程标准（第 2.4 节）要求、但没有任何已批准页面展示的状态或角色，必须在同一 Gate 中作为显式扩展提出。例如 danger、error、success、warning、disabled、pending、selected 和 empty。每项扩展记录在 `10-design-tokens.md` 的状态矩阵中，并在组件样例中展示。Token 不得让任何必需状态处于未定义状态，页面上没有出现不能成为省略的理由。扩展必须保持在已批准的视觉姿态之内，并由用户与基线一起批准。提供层级和图层刻度，以及包含减少动态效果行为的动效决定。如果已批准方向有意不设这些，则记录这一点及理由。

该产品的结构化 Token 存在其设计包的 `tokens/design-tokens.json`。后一个产品不覆盖另一个产品的 Token 文件。在 `10-design-tokens.md` 记录理由和使用方式。于 `11-component-specifications.md` 定义核心组件结构、变体、状态、无障碍、键盘行为和使用规则。提供可审阅的 Component Gallery/样例。先调研现有技术栈，再决定 Token 输出格式和映射策略。不得增加运行时依赖或应用代码。等待用户批准 Token 基线、状态矩阵和核心组件系统。

### Stage 4 — 线框和页面规格
使用已批准 IA 和组件契约，创建可编辑、可审阅的低保真线框及页面规格。定义布局区域、信息层级、控件、窗口缩放行为、键盘/焦点顺序和相关状态。每个页面映射 PRD AC 和用户流程。高保真设计前先解决结构问题。

### Stage 5 — 高保真视觉设计和交互规格
将已批准 Token/组件应用于所有范围内页面。依据已批准的状态矩阵定义适用状态，并定义交互，包括 PRD 要求的校验、成功/失败/取消、权限拒绝、破坏性操作确认、加载/空/错误和本地时间边界情况。记录页面级偏差及理由，不增加未经支持的产品行为。

### Stage 6 — 设计系统和视觉验证
把高保真规格与 Gate 1 已批准的页面集、Token、组件规范、页面规格、无障碍和需求追溯对照验证。检查 Token 覆盖、任意值例外、组件复用、字体/间距层级、状态矩阵覆盖、窗口尺寸行为和跨页面一致性。

必须有渲染证据。把已批准页面和每个范围内的高保真屏幕或样例，在一个窄视口和一个宽视口各渲染一次；存在平台真实渲染器时使用真实渲染器。保存带视口元数据的命名截图。测量每一对文字/背景以及每个焦点指示器的对比度，对照适用的 WCAG 标准并记录比值。对照视觉简报的形容词和反目标检查每张渲染屏幕，并为每一条记录 PASS 或 FAIL。以上全部记录在 `13-visual-validation.md`。

缺少证据即为 NOT RUN，绝不是 PASS。渲染证据为 NOT RUN 的设计包不得离开 Stage 6。安装截图或测量工具属于依赖变更，需要单独授权。没有授权时把证据标记为 NOT RUN 并说明，不得用文字描述代替截图。

本阶段比较的是设计产物和已批准页面集。运行中的实现与同一页面集的比较属于另行授权后的 Coding & Testing 阶段。

### Stage 7 — 独立设计评审 Gate
Stage 1–6 形成完整一致的设计包后，委派独立 Reviewer。向 Reviewer 提供已确认的简报和截图文件。Reviewer 读取图片，除既有检查外，还就简报契合度、视觉层级和状态覆盖返回 findings。没有截图的评审必须声明视觉质量为 NOT REVIEWED。报告保存至 `08-design-review.md`。每项 finding 记录严重程度、证据、场景、影响、建议和是否需要产品决策。主设计者处理设计问题；产品决策交由用户。重大修改后重新评审。

### Stage 8 — 实施就绪和用户批准
检查每个适用 PRD AC 是否映射到流程/页面/组件/交互或有合理的非 UI 说明；UI 契约是否符合 Technical Design；Token/组件/页面/状态/无障碍覆盖是否完整；渲染证据是否齐备或已记录为 NOT RUN；findings 是否解决或明确跟踪；UI 任务是否与 Implementation Plan 对齐。计划变更必须先提交用户批准，不得静默应用。用户明确批准前状态保持 READY FOR USER REVIEW。

### Stage 9 — 交接
UI/UX 获批后准备设计交接及已批准的计划变更。交接文档把范围约束和品味约束分节列出。交接不等于编码授权；必须等待用户单独明确授权才能开始实现。

## 6. Token 和组件治理

- Token JSON 是已批准设计值的机器可读取来源；Markdown 说明语义、理由、约束和示例。
- 英文设计文档为规范版本；对应 `-zh.md` 为翻译，必须保持语义一致。
- 使用三层 Token：Primitive（原始值）、Semantic（用途别名）、Component（组件专属别名）。页面规格存在 Semantic Token 时不得直接引用 Primitive。
- Stage 2 用户批准和 Stage 3 提取前不得编造最终 Token 值；临时值必须明确标注。Token 记录已批准页面集上可见的决定，以及用户批准的 Stage 3 扩展。
- 页面必须使用已批准的 Semantic/Component Token。例外必须记录理由并由设计系统负责人/用户处理。
- 层次、字体、间距、颜色或组件行为的变更，先更新已批准页面集并等待批准，再更新受影响的 Token 和屏幕。
- 组件规范应定义用途、结构、变体、状态、键盘/无障碍行为、缩放、使用方式和反例。
- 影响多个页面的 Token/组件变更必须分析影响并更新相关规格，不得暗中分叉设计系统。

## 8. 适用范围与迁移

- 本工作流适用于本仓库的每个产品和项目，也适用于所有由本工作流启动的新项目。除非按 `docs/ui-ux/ENGINEERING-STANDARD.md` 第 1 节记录了理由、批准人和复查日期的偏差，项目不得跳过视觉简报、页面集、状态矩阵或渲染证据。
- 本仓库之外的项目通过 `docs/ui-ux/PROJECT-ADOPTION-CHECKLIST.md` 采用本工作流，并记录所遵循的工作流版本。
- 早期工作流版本下批准的视觉权威在用户批准替换方案之前继续有效。3.0.0 版本约束所有新的或替换的方向，不会重新打开已有的批准。

## 9. 为什么有 3.0.0 版本

Personal Time 网站最初按 Agenda 方向构建，后来被现代化工作区设计取代。仓库历史显示了原因，每一条都对应上面的一条规则。

| Agenda 设计包中的原因 | 本版本中的规则 |
|---|---|
| Token 只从一张 111 行的单页提取。没有 danger、error、disabled、pending 或层级 Token，交接文档还写明没有危险色。 | Stage 3 状态矩阵和必需的扩展 |
| 一条品味偏好（单列、无导航栏、无卡片）与真正的范围排除并列写在交接文档里。 | 第 4A 节 |
| 两个方向都来自安静的列表型参考，工作流点名的参考族是克制的工具风格。 | Stage 2 视觉简报、姿态不同的方向、无默认参考族 |
| 没有简报说明产品应该给人什么感觉、绝不能给人什么感觉。 | 带反目标的 Stage 2 视觉简报 |
| 验证记录写明对比度未测量、未截取屏幕截图。 | Stage 6 渲染证据、Stage 7 图片评审 |
| 一次微调只改了 CSS，没有改 Token 基线，所以抛光无法修复系统层的缺口。 | Stage 3 扩展，以及页面工作前的 Gate 2 批准 |
